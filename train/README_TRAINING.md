# 小K 的"独立核心模型"——架构说明与使用指南

这份文档回答的问题是：**怎么让小K拥有不依赖任何厂商的、自己的思维和记忆，
并且能通过日常使用不断变强。**（"记忆"具体怎么分层、存在哪，见
[`docs/MEMORY_MODEL.md`](../docs/MEMORY_MODEL.md)；换 base model 时怎么完整
继承，见 [`README_INHERITANCE.md`](README_INHERITANCE.md)）

## 二、日常怎么用（不需要你操心训练细节）

正常聊天就行。系统在后台做的事：

1. 每次你的对话被路由到一个**在线**教师模型（siliconflow/openrouter/glm/anthropic）
   且**不是**离线降级产生的回答时，这轮 `(system_prompt, 你的输入, 模型回答)`
   会被记进 `memory/training_samples.db`——这是以后训练本地模型的原材料。
2. 网页版每条回复下面会出现 👍/👎，CLI里可以用 `/good` `/bad` 给上一条评价。
   点踩的样本默认不会被用于训练。
3. `/trainstats`（CLI）或 `GET /api/training_stats`（网页版接口）随时看攒了多少数据。

**你完全不用管这些**，攒够了再去跑训练脚本就行。

## 三、什么时候、怎么训练

你有独立GPU，这条路径对你是可行的：

```bash
# 0. 训练用的Python环境不依赖日常聊天用的那个venv，你可以按自己机器情况
#    单独选Python版本/环境（只要下一步能装上 requirements-train.txt 即可）

# 1. 只在训练机器上装一次（体积较大，故意没放进日常的 requirements.txt）
pip install -r requirements-train.txt

# 2. 先看看攒了多少数据，不实际训练
python train/train_lora.py --dry-run

# 3. 攒够 config.yaml -> training.lora.min_new_samples_to_train（默认150条）之后
python train/train_lora.py
```

训练用的是 **QLoRA**（4bit量化 + LoRA适配器），不是全量微调：
- 显存需求小（3B模型量级大约6-8GB），你的GPU应该够用
- 产出的是几十MB的 adapter，不是几个GB的完整模型，方便版本管理和回滚
- base model 默认是 `Qwen/Qwen2.5-3B-Instruct`（`config.yaml -> training.lora.base_model`
  可改），比断网兜底用的1.5B模型能力更强——**这里刻意把"训练用的base"和
  "日常兜底跑的模型"分开配置**，因为前者只在你GPU机器上跑一次性训练，
  后者要在任意笔记本CPU上日常跑，需求完全不同。

训练完成后，`data/adapters/vN/eval_report.json` 里会有**训练前后**在固定测试集
（`data/eval/eval_set.jsonl`，已经放了8条覆盖身份/推理/代码/安全边界的起始用例，
**建议你自己再补充几条你关心的场景**，比如GSG探针相关的专业问题）上的输出对比。

**这一步需要你自己人工看一眼**，确认：
- 身份认知没丢（还知道自己是小K）
- 安全边界没有因为蒸馏数据被带偏（比如那条"写病毒代码"的测试还在拒绝）
- 专业问题的回答质量确实比训练前更好

确认没问题后，脚本末尾注释里有合并 adapter 并转换成 GGUF 的步骤，把新模型接进
`local_fallback`。**没有做自动切换**，是故意的——训练效果好坏你说了算，不希望
一个训练脚本自动替换掉正在用的模型。

## 四、为什么现在没做"本地模型做主控大脑"这种彻底重构

你原话里"思维不受接入模型影响"，最彻底的做法是把架构反过来：

```
现在:  用户输入 -> 选一个provider(在线/本地) -> 直接对话 -> 记忆只是"背景知识"
理想:  用户输入 -> 本地核心模型先理解/规划 -> 需要时把子任务外包给在线大模型 -> 
       本地核心模型整合结果、决定怎么回答、怎么写记忆 -> 输出
```

这样不管接不接在线模型，"怎么想问题"这件事的决策权始终在本地模型手里，
在线模型退化成"知识/算力外挂"而不是"人格来源"。

**这次没做**，原因是这是个数量级更大的改动（每轮对话至少多跑一次本地推理，
对低配笔记本会有明显延迟；子任务拆解/外包逻辑本身也需要专门训练或者精心设计
的提示词工程），而且**没有第三节那套训练数据积累机制，本地模型强不到能
胜任"主控"角色**——所以这次先把地基（数据怎么攒、怎么练、怎么评估）搭好，
等你本地模型经过几轮蒸馏训练、在 `eval_set.jsonl` 上表现稳定之后，再做这个
架构反转会更踏实，不然"主控"的是一个能力很弱的模型，体验反而会变差。

对应 README.md 里的路线图阶段7。

## 五、给 DPO（偏好对齐）留的扩展点

现在 👍/👎 只用来"筛掉训练数据里的坏样本"。更进一步可以做：每次线上教师模型
回答之前，先让本地小模型自己生成一版答案（不展示给你，纯后台），教师模型的
回答标为 chosen，本地模型的答案标为 rejected，配对起来做 DPO 训练——这样
本地模型不仅学"教师说了什么"，还学"教师的答案比我自己原本会给的答案好在哪"，
比纯 SFT 蒸馏收敛更快。这个需要在 `agent.py` 里加一次额外的本地模型推理调用，
会增加每轮对话的延迟，所以先没做，留在你觉得当前蒸馏效果不够时再加。
