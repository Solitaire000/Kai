# 硬件接入架构

这份文档回答的问题：小K怎么接入真实的物理硬件（第一个例子是 Seeed
MR60BHA2 毫米波呼吸心率传感器），同时满足三个硬性要求：

1. **不影响网页端正常对话**——硬件的连接、读取、断线重连，都不能阻塞
   聊天请求的处理。
2. **体现agent的智能性，不是简单条件判断**——不能写"心率>120就报警"这种
   硬编码规则，硬件数据该怎么解读、要不要提醒用户，应该是模型自己结合
   对话上下文推理的结果。
3. **可扩展**——这次只接入一个硬件，以后还会接入其它硬件，新增硬件时
   改动范围要小、模式要能复用。

设备接入的具体操作步骤在 [`../hardware/README.md`](../hardware/README.md)；
MR60BHA2 这个具体设备的接线/烧录/排障在
[`../hardware/devices/mr60bha2_breath/README.md`](../hardware/devices/mr60bha2_breath/README.md)。
这份文档只讲**架构层面为什么这么设计**。

---

## 一、整体拓扑

```
┌─────────────┐   板载UART    ┌──────────────┐   USB(虚拟串口)   ┌──────────────────┐
│  雷达模块      │ ───────────▶ │ XIAO ESP32C6  │ ─────────────▶  │   运行小K的PC       │
│ (MR60BHA2)   │  (套件已接好)  │  (烧录固件)    │  (JSON信封协议)   │  Python主进程      │
└─────────────┘               └──────────────┘                  └──────────────────┘
   厂商私有协议                  固件内部用Seeed官方库                 core/hardware_manager.py
   （闭源）                      讲这个私有协议，对外                   在后台线程里读取，
                                只暴露统一JSON格式                     内存缓存最新状态
```

小K是运行在PC端的智能体（不是跑在ESP32上），这一点决定了整个架构的形状：
ESP32只是一个"翻译官"——一边讲雷达模块的私有协议，一边把翻译好的结果用
一份自定义的、通用的JSON格式喂给PC。PC端的Python代码完全不需要知道雷达
模块本身是怎么通信的。

## 二、分层设计

```
┌────────────────────────────────────────────────────────────────┐
│ 固件层（设备专属）  hardware/devices/mr60bha2_breath/firmware/     │
│   讲雷达模块的私有协议，输出统一JSON信封（"kai-hw/1"协议）           │
├────────────────────────────────────────────────────────────────┤
│ 传输层（通用，所有USB串口设备共用）  hardware/serial_transport.py   │
│   端口发现(VID/PID)、后台线程读取、断线自动重连                     │
├────────────────────────────────────────────────────────────────┤
│ 驱动层（设备专属，但接口统一）  hardware/devices/<name>/driver.py   │
│   解析JSON、维护内存状态、实现 HardwareDevice 接口                 │
│   (hardware/base_device.py)                                     │
├────────────────────────────────────────────────────────────────┤
│ 管理层（通用）  core/hardware_manager.py                          │
│   发现所有设备驱动、非阻塞启动、统一工具注册表接口                    │
├────────────────────────────────────────────────────────────────┤
│ Agent层  core/agent.py                                          │
│   工具分发(_tool_registry)、system prompt说明、写入记忆            │
└────────────────────────────────────────────────────────────────┘
```

每一层只依赖下一层暴露的统一接口，不依赖具体实现细节。新增一个硬件设备时，
只需要新写"固件层"+"驱动层"这两层里设备专属的部分（而且如果新设备也是走
USB串口，"传输层"可以直接复用 `serial_transport.py`），"管理层"和"Agent层"
完全不用改——这是满足"以后还会拓展其它硬件"这个要求的核心设计。

## 三、为什么不阻塞：非阻塞是贯穿全链路的约束

**网页版每次请求都是一次独立的HTTP调用**（`web_app.py::api_chat`），这个
请求处理线程如果去做任何可能耗时/可能失败的硬件I/O（比如打开串口、等待
一次读取），轻则拖慢响应，重则因为串口异常直接卡死整个请求。所以硬件层
的设计里，**任何"和硬件本身说话"的操作，只发生在专门的后台daemon线程里**：

- `HardwareManager.__init__()` 只做两件快速的事：扫描 `device.yaml` 清单
  文件（纯本地文件读取，很快）、调用每个设备驱动的 `start()`。
- `driver.start()` 内部立刻返回——真正连接串口、读取数据，都在
  `SerialLineReader` 起的后台线程里做，遇到"设备还没插上""连接断开"这些
  情况，只是在后台线程里悄悄重试（带退避），永远不会抛异常到调用它的地方。
- Agent层（`core/agent.py`）调用硬件工具（比如 `read_vital_signs`）时，
  实际发生的只是**读一次被锁保护的内存dict**（`driver._state`），不是真的
  实时去问一次硬件——这个操作是微秒级的，不会拖慢对话响应。

一句话：**网页请求线程自始至终只读缓存，从不等待硬件**。这也是为什么
"未连接"这件事不是异常，而是 `execute()` 返回的一个普通的
`{"ok": False, "error": "..."}` 结果——模型会正常收到这个结果，可以正常
组织语言告诉用户"传感器好像没连上"，而不是导致整个请求失败。

## 四、智能性体现在哪：观测和决策分离

这是需求里"要体现agent的智能性，而不是简单的条件判断"的具体落地方式，
分两条路径：

### 4.1 主动查询路径（模型自己决定要不要看数据）

`read_vital_signs` 就是一个普通的、纯读取型的工具，和 `get_datetime` 没有
本质区别——它不会自己触发任何行为，只有模型主动调用它才会返回数据。
`core/agent.py::_build_tools_explainer()` 只是告诉模型"这个工具存在、能用
来查什么"，不会告诉模型"什么时候必须调用它"。模型自己判断——比如用户提到
"最近感觉有点累""心慌"，或者直接问"我现在状态怎么样"，模型可以自主决定
调用一次 `read_vital_signs` 再回答，也可以判断这次不需要查，就是普通聊天。

**这里没有任何"if 关键词命中就强制调用"的路由规则**——工具会不会被调用，
完全由模型基于对话上下文的语义理解决定，和 `skills/`、`consult_subagent`
走的是同一套"模型自主决策该不该调用工具"的机制，没有为硬件单独开一条
"更聪明"或"更笨"的路径。

### 4.2 被动观测路径（后台记录事实，模型决定怎么用）

传感器数据是持续产生的（比如每0.5秒一帧），不可能每一帧都去打断模型、
问它"要不要看看这个"——那样既浪费调用，也会让对话变得很奇怪。所以设计上
分成两步，**关键是这两步的职责边界**：

1. **驱动层只负责"记录发生了什么"**：`driver.py` 里的
   `_maybe_emit_event()` 只在状态发生了"值得记一笔"的变化时（比如
   presence 从无人变成有人），把这句大白话式的观察结果（"检测到有人进入
   检测范围，呼吸率约16.2次/分"）写进记忆——**不判断这个数值正不正常、
   要不要紧、该不该提醒**，纯粹是"记一笔事实"，逻辑上和"用户刚才说了句
   话"没有区别，都只是往 `core/memory.py` 的 episodic 表里加一条记录。
2. **模型层负责"这件事重不重要、该怎么回应"**：`core/agent.py::_build_messages()`
   每轮对话都会把最近几条硬件观测取出来（`memory.recent_by_tag("hardware")`），
   作为"仅供参考的原始事实"注入 system prompt，明确告诉模型"要不要提、
   怎么提，你自己判断"。模型可能在这轮对话里主动提一句关心，也可能觉得
   不相关完全不提——**这个判断本身就是"agent的智能性"，而不是Python代码
   里写死的 `if heart_rate > 120: send_alert()`**。

这个设计还有一个好处：即使以后要接入的硬件产生的是完全不同性质的数据
（比如温湿度、门禁状态），"观测→记忆→模型自己判断"这条路径不用改，只是
驱动层往记忆里写的那句话内容不同而已。

## 五、命名冲突防护：三类工具共享同一个命名空间

`consult_subagent`、`skills/` 下的技能、硬件设备暴露的工具（比如
`read_vital_signs`），最终都会被塞进同一份 `tools=[...]` 参数传给模型，
也就共享同一个"工具名"命名空间。`core/agent.py::KaiAgent.__init__()`
构造时，会把 `SubAgentManager.tool_names()` 和 `HardwareManager.tool_names()`
的并集，作为保留名单传给 `SkillsManager`——如果哪个 `skills/` 下的技能
`name` 刚好撞车，会被跳过加载并打印警告，而不是静默生效后被
`core/agent.py::_tool_registry()` 的查找逻辑永久覆盖（因为 dict 后写入的
键会覆盖先写入的）。完整说明见 [`docs/TOOLS_VS_SKILLS.md`](TOOLS_VS_SKILLS.md)。

## 六、统一工具注册表：新增硬件不需要改分发逻辑

`core/agent.py::_tool_registry()` 构建一份 `{工具名: manager}` 的字典，
`SkillsManager`/`SubAgentManager`/`HardwareManager` 三者都实现了同一套
接口（`tool_names()`/`is_dangerous()`/`auto_confirm_enabled()`/
`preview()`/`execute()`）。`_run_tool_loop()` 分发工具调用时，只需要
`registry.get(call["name"])` 查出是哪个manager负责，调它的 `execute()`
就行，**不需要为每种工具来源写一个 `if call["name"] == "xxx"` 的分支**。

这个设计不是新硬件专门加的，是这次为了干净地接入硬件、顺带把之前
"只有 skills 和 consult_subagent 两种、勉强还能各写一个if分支"的写法
提前通用化了——以后不管是加第二个硬件设备，还是加一整个全新种类的工具，
都只需要实现同一套接口塞进 `_tool_registry()` 汇总的三个来源里，不需要
碰 `_run_tool_loop()` 内部的分发逻辑。

## 七、危险操作/确认机制：为未来的执行器类硬件预留

MR60BHA2 是纯读取型传感器，`is_dangerous()` 恒为 `False`，不会触发确认
流程。但架构上这个口子是留好的：如果以后接入的硬件带执行器（比如控制一个
继电器、舵机，会真正对物理世界产生动作），驱动只需要把对应工具的
`is_dangerous(name)` 返回 `True`，并实现 `preview(name, params)` 给出一段
确认文案，就能直接复用和 `skills/` 里"危险技能"完全一样的用户确认流程
（`core/agent.py::_run_tool_loop` 统一处理，网页版对应的"待确认卡片" UI
也不需要改）。

## 八、通用JSON协议："kai-hw/1"

完整定义在 [`../hardware/README.md`](../hardware/README.md)，这里只强调
设计意图：**PC端只认识这一份自定义的、跨设备通用的JSON信封格式，不认识
任何一个具体厂商的私有协议**。厂商协议多复杂、多闭源，都被封装在贴身的
固件里，换一个厂商的设备，只要新固件也讲这份JSON，PC端的
`hardware_manager.py`/`serial_transport.py` 完全不用动，只需要照抄一份
`driver.py` 模板。

## 九、已知限制 / 后续可以做的事

- **自动端口识别不保证100%准确**：不同批次的USB转串口芯片，VID/PID可能
  有细微差异，`config.yaml` 里始终保留手动指定 `port` 的兜底选项。
- **固件里具体的 `mmWave.getXxx()` 方法名未经真实硬件验证**：本次开发
  环境里没有实体硬件可供烧录测试，固件代码是参照官方文档的用法模式写的，
  使用前需要对照 Arduino IDE 里的官方 `mmWaveBreath` 示例核对方法名，
  详见固件文件里的注释和设备 README。
- **目前只支持 USB-串口连接方式**：以后如果要接蓝牙/网络类硬件，
  `hardware/base_device.py` 的接口本身与连接方式无关（`start()`/`execute()`
  这些方法不关心底层怎么连接），可以照着 `serial_transport.py` 的模式再写
  一个 `ble_transport.py`/`network_transport.py`，不需要改动更上层的代码。
- **硬件观测事件目前没有做去重/合并之外的智能筛选**（比如没有区分"这次
  观测和三个不同硬件同时报告"之类的关联分析）——如果以后硬件数量变多，
  可以考虑在 `core/agent.py` 里对多个硬件观测做一次轻量的合并整理再注入
  system prompt，避免上下文被过多硬件事件占用。
