# 小K（kai_agent）迭代优化方案 v2

> 本版相较于第一版方案的核心调整：不再追求"框架自研程度"，转而追求"记忆内容的不可替代性"。
> 一句话定位：**小K的本体是记忆体系，不是模型，也不是框架代码本身**——框架会被开源生态追平，记忆里那些无法被推断、只能被经历的具体信息，不会。

---

## 一、总纲：这一版方案建立在四个判断之上

在具体优化项之前，先把支撑这份方案的核心判断写清楚，后续所有优先级排序都由此推导：

**判断一：框架能力会被开源生态持续拉平，这是必然趋势，不必对抗。**
2026年的开源生态里，Mem0、Zep/Graphiti、Letta等记忆框架，OpenClaw这类本地优先的行动执行框架，Second Me这类个人数字分身项目，在各自单一维度上已经比小K现在的自研实现更成熟。继续在"记忆分层怎么设计得更精巧""路由逻辑怎么写得更优雅"这类框架细节上死磕，边际收益正在下降。

**判断二：性格/风格类信息会被模型的少样本推断能力逐渐"免费"获得，这部分不值得重投入。**
一个足够聪明的模型，未来只需要很少的样本就能推断出一个人大致的表达习惯、思维方式、性格轮廓——因为这是"统计意义上可泛化的模式"。这部分投入（尤其是LoRA性格微调）的必要性会随模型进步持续走低。

**判断三：具体事实和经历不可被推断，只能被记录，这是唯一不会被技术进步拉平的部分。**
不管模型多聪明，都无法在没有被告知的情况下，知道你某个具体项目在某个具体时间点做过的具体决策——这不是算力问题，是信息论层面的硬限制。模型"猜"出来的东西，本质是统计规律套用，不是真正的了解。这部分才是记忆资产里真正值得长期投入、且投入时间越早复利越大的核心。

**判断四：硬件感知与真实物理环境的绑定，是目前开源生态里少见的差异化能力，值得继续深挖。**
搜索现有开源方案后确认，"传感器数据接入记忆和决策闭环"这类设计在主流个人agent项目里覆盖较少，是小K相对独特、值得优先投入的方向之一。

## 二、架构策略调整：从"自研优先"转向"整合优先"

这是本版方案相较v1最大的方向性调整。

### 2.1 记忆引擎：评估接入成熟开源方案，而不是继续手写

- **为什么调整**：现有的三层记忆+向量检索设计方向没有错，但持续手工打磨检索精度、时效性建模（"记忆是否过期"）这类问题，专业团队已经做得更好。比如时效性事实建模（把每条记忆当作带有效期的图节点，而不是静态字符串），是当前自建方案里缺失、但对"记忆准确反映当下的你"很关键的一块。
- **怎么做**：
  - 调研接入Mem0或Graphiti作为底层记忆引擎的可行性，评估是否能直接替换/增强`core/memory.py`的检索层，而不是继续从零打磨
  - 保留自己的分层设计思路（运行时记忆 vs 训练侧资产的划分依然是对的），但把"如何检索得更准"这个工程问题尽量交给成熟组件
  - 迁移过程中严格保证`memory/identity/`和`memory/knowledge/`这两块纯文本资产的独立性，不因为换引擎而被绑死在某个厂商的存储格式里

### 2.2 行动执行层：参考OpenClaw等成熟方案的设计模式

- **为什么调整**：v1方案里"主动观察-建议闭环""跨skill任务编排"这两项，本质上是本地优先、24/7行动型agent的标准能力，OpenClaw这类项目已经跑出了成熟形态（ReAct推理执行+插件化技能+多渠道集成）。
- **怎么做**：
  - 不必照搬整套框架，但值得研究其skill插件化的接口设计和权限模型，看看能否优化`skills/README.md`里定义的扩展接口
  - 优先复用其成熟的"任务规划-分步执行-结果反馈"模式，而不是自己从零设计一套编排逻辑

### 2.3 明确"自研 vs 整合"的判断标准

以后每次面临"这块要不要自己写"的选择，用这个问题判断：**这是在解决一个通用的工程问题（检索算法、执行编排、并发安全），还是在处理一个只有小K的具体场景才需要的问题（你的记忆内容结构、你的硬件设备、你的身份锚定语料）？** 前者优先找成熟方案整合，后者才值得自己投入时间打磨。

## 三、记忆策略调整：从"记录得多"转向"记录得对"

这是本版方案里最重要的思路转变，直接决定了`training_samples.db`和`memory/knowledge/`未来该攒什么样的数据。

### 3.1 区分两类记忆，投入优先级完全不同

| 类型 | 特征 | 未来会不会被模型"免费"推断出 | 投入策略 |
|---|---|---|---|
| 可泛化模式 | 说话习惯、常用语气、性格倾向、通用工作风格 | 会，且成本持续走低 | 保持轻量，不必刻意大量收集，未来靠模型自身能力兜底 |
| 不可替代事实 | 具体项目的具体决策、具体bug的具体解法、具体取舍背后的具体原因、和你个人经历直接绑定的细节 | 不会，模型无法凭空得知未发生在它数据里的事 | 优先记录，越早积累越占优，这是真正的护城河 |

### 3.2 具体执行建议

- **写入`memory/knowledge/`时，优先标注"这条信息是否可以被合理推断"**。如果一条记忆是"我倾向于简洁直接的沟通风格"，这类可以打低优先级标签；如果是"GSG探针项目里`missing_area_ratio`那次观测-物理形状混淆的具体修正方案和采纳原因"，这类要重点保留完整上下文，不只存结论，连"为什么这么决定"的推理过程一起存。
- **`training_samples.db`的蒸馏语料收集，向"决策留痕"倾斜**，而不是单纯堆积日常对话量。日常寒暄类对话的边际价值最低，具体的技术决策、具体的取舍权衡过程，边际价值最高且不可替代。
- **定期审视已有记忆，识别哪些是"泛化模式"、哪些是"具体事实"**，逐步把两类分开存储和分开检索权重，检索时对"具体事实"给更高优先级，因为这才是真正体现"独属于你"的部分。

## 四、LoRA的最终定位：窄范围工具，不进主线

结合前面的讨论，LoRA在整个方案里的位置进一步收窄：

- **不用于记忆**：记忆永远走上下文注入/检索路径，这一点已经明确，不再赘述。
- **不用于通用性格固化**：性格属于"可泛化模式"，模型的少样本推断能力会持续降低这个需求的必要性，提前重投入的性价比在下降。
- **仅保留一个场景**：本地模型在某个高频、具体、prompt反复调试依然不稳定的行为模式上的补丁式微调。触发条件不变——问题具体、高频出现、且已有对应类别的数据积累到位，三者同时满足才启动，且视为一次性checkpoint，不追求持续迭代。

## 五、硬件感知：保留并优先强化的差异化方向

这是搜索现有开源生态后，明确识别出的"别人还没做透"的方向，建议在资源分配上给予比v1更高的优先级。

- **传感器数据接入记忆时间线**：把mmWave呼吸心率数据和你的日常状态、工作节奏关联起来，形成"生理-行为"的联合记录，而不只是孤立的读数。
- **决策层真正利用感知数据**：比如结合作息数据主动建议休息，这一步目前在开源生态里少见对应实现，值得持续投入。
- **后续可扩展的方向**：环境光、噪音等更多传感器，构建更完整的物理环境感知层，这条路线的独特性会随投入时间持续累积，不会被"部署一个开源框架"轻易复制，因为复制框架容易，复制"和你的具体设备、具体环境磨合出的经验"难。

## 六、迭代路线图（更新版）

### 阶段一（近期，1–2个月）：地基与评估

| 事项 | 说明 | 为什么 |
|---|---|---|
| 记忆资产备份与版本化 | 对`identity_anchors.jsonl`和`memory.db`做定期快照+Git版本化 | 唯一不可逆的资产，必须最优先兜底 |
| 调研Mem0/Graphiti接入可行性 | 评估能否替换/增强现有检索层，尤其关注时效性事实建模能力 | 把工程精力从自研检索转向内容积累 |
| 操作审计日志 | write_file/run_command/硬件控制类操作全记录 | 后续扩大行动权限的前提 |
| eval回归测试落地 | 记忆检索准确性+身份一致性最小可用测试集 | 防止接入新框架或调整代码时破坏既有效果 |
| 记忆分类标注试点 | 对现有`memory/knowledge/`做一次"可推断 vs 不可替代"分类梳理 | 建立后续记忆收集的判断标准 |

### 阶段二（中期，3–6个月）：整合与行动闭环

| 事项 | 说明 | 为什么 |
|---|---|---|
| 记忆引擎整合落地 | 完成Mem0/Graphiti（或同类方案）的实际接入 | 用成熟组件补齐检索精度和时效性短板 |
| 参考OpenClaw完善skill编排 | 优化任务规划-分步执行-反馈机制 | 从被动响应走向主动行动 |
| 主动观察-建议闭环 | 日程提醒、传感器异常提醒等最小场景落地 | 决定"是助手还是工具"的分水岭 |
| 可信执行反馈机制 | 操作后清晰反馈依据和撤销方式 | 建立敢于放权的信任基础 |
| "决策留痕"式记忆收集规范化 | 明确记录具体技术决策的完整推理过程，不只存结论 | 积累真正不可替代的记忆资产 |

### 阶段三（长期，6–12个月以上）：差异化深挖与验证

| 事项 | 说明 | 为什么 |
|---|---|---|
| 硬件感知-决策打通 | 生理数据、环境数据真正影响主动建议 | 目前开源生态最少覆盖的差异化方向 |
| 真实换基座模型演练 | 验证记忆资产迁移的完整性 | 检验"记忆模型无关"这一核心假设是否真的成立 |
| 记忆检索质量持续复盘 | 定期review哪些记忆被高频命中、哪些从未使用 | 记忆质量的长期复利优化 |
| 视情况启动一次LoRA补丁 | 仅当满足前述三个触发条件时 | 窄范围工具，不作为常态任务 |

## 八、验收标准

- **阶段一完成标志**：记忆库有可用历史快照；审计日志可完整回溯最近一周高权限操作；建立了"可推断 vs 不可替代"的记忆分类标准并应用到新数据收集中。
- **阶段二完成标志**：至少一个成熟记忆引擎完成接入且检索效果有对比验证；至少一个主动提醒场景稳定运行；决策类记忆收集有明确、可执行的记录规范（不只存结论，存推理过程）。
- **阶段三完成标志**：换过一次基座模型且记忆/人格无损；传感器数据真正影响过一次实际决策建议；如果启动过LoRA，有明确的效果评估证明确实解决了prompt无法解决的问题。

## 九、写在最后：这份方案真正想说的一件事

这一轮方案调整的核心，不是"多做点什么"，而是"少纠结于什么，多投入到什么"。

框架代码写得多精巧、检索算法调得多优雅——这些会被开源生态持续追平，不必在这上面死磕，该用成熟方案就用。性格像不像你、语气对不对——这部分模型会越来越聪明地自己猜出来，不必提前重投入。

真正值得你花时间的，只有一件事持续没有变过：**尽早、持续地把那些"只有真实发生过才会存在"的具体经历、具体决策、具体推理过程，如实记录进小K的记忆里**。这件事没有捷径，任何技术进步都无法帮别人替你补上"没有经历过的过去"，这才是三年后、五年后，别人的agent不管部署得多快、框架多成熟，都无法拥有的东西。

框架是租得到、买得到、甚至抄得到的，时间不是。
